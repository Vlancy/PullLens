Using PullLens

Secret scanning

Every pull request diff is checked for leaked credentials with gitleaks - free, independent of the AI reviewer, and with nothing sent to any AI provider.

What it does

PullLens runs gitleaks (MIT-licensed) against the lines a pull request adds - API keys, tokens, private keys, passwords, the usual shapes a secret takes. It never clones the repository: only the added lines from the diff are scanned, so this is fast and does not depend on repository size.

The scan has its own check run and does not touch your AI budget. It runs whether or not Enable reviews is on, and whether or not an AI provider is even configured.

When it runs

On every pull request event that introduces code: opened, synchronised (a new commit pushed) and reopened. Each run scans the diff at the new head commit.

Where results show up

A hit is reported in four places at once:

WhereWhat you see
The pull requestAn inline review comment on the exact line, redacted, telling the author to rotate the credential - removing the line is not enough.
The Security pageA critical finding on the Secrets tab, tracked through to resolution like any other finding.
The PullLens / Secrets checkA dedicated GitHub check run - failure when something is found, success when the diff is clean, neutral if the scan itself could not run.
A git noteWritten under refs/notes/gitleaks on the scanned commit, redacted, for a permanent record outside PullLens.

Every one of these shows the secret redacted. PullLens never re-displays the value it found, anywhere.

Reading the git notes

GitHub's web UI does not show notes, so read them from a clone:

git fetch origin refs/notes/gitleaks:refs/notes/gitleaks
git log --notes=gitleaks

Allowlisting test fixtures

Some repositories deliberately keep fake secrets around for tests. Allowlist them by committing a .gitleaks.toml or .gitleaksignore to the pull request's target branch - main, or whatever it is merging into.

[[allowlists]]
description = "known test fixtures"
paths = [
  '''tests/fixtures/.*''',
]

See gitleaks's own configuration reference for the full [[allowlists]] syntax - paths, regexes, stopwords and commits.

What a pull request cannot do

A pull request can never allowlist its own secret. PullLens reads .gitleaks.toml and .gitleaksignore only from the target branch, never from the pull request's head, so a config file the PR adds or edits is ignored for that scan. Inline gitleaks:allow comments the pull request adds are ignored for the same reason. If a fixture needs allowlisting, commit the config to the target branch first, in its own change.

How findings resolve

SituationOutcome
The secret is no longer in the diff on a later pushResolved automatically as Secret removed from diff - not a manual option, only ever set by a rescan - with a reply that it is still in git history and should be rotated.
A human marked it false positive, won't fix, or acknowledgedStays resolved on later pushes; the same secret does not reopen it.
A human marked it fix submitted or fix confirmed, but the same secret is still thereReopens as a fresh finding - both resolutions claim the secret is gone, and it plainly is not.

Turning it off

Per repository, under Settings → Repository → Security. It is on by default; turning it off stops new scans for that repository without touching its history of past findings.

Limitations

  • Only the pull request's final diff against its target branch is scanned. A secret added in one commit and removed again before the pull request is scanned - within the same pull request - never appears in that diff and is not detected, even though it remains in the branch's commit history.
  • Without the gitleaks binary on the server, scans are skipped and a warning is logged - no check run is created, and nothing blocks the pull request.
  • The hourly scheduler sweep that deletes leftover scan workspaces needs the Laravel scheduler running; see Installing PullLens.
