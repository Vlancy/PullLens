Getting started

Installing PullLens

PullLens runs on your own machine or server. The installer handles Docker, the containers, the database and the first admin account.

Before you start

You needNotes
A Linux or macOS machineA small VPS is plenty. Two CPU cores and 2 GB of RAM handles a normal team.
DockerThe installer offers to set it up if it is missing.
An AI provider API keyFrom Anthropic, OpenAI, Google and others - or none at all if you plan to run Ollama locally.
Admin access to your GitHub orgNeeded once, to create the GitHub App.
A public URL for webhooksGitHub must be able to reach your instance to send pull request events. A tunnel works for trying it out.

Install

One command on a fresh server:

curl -fsSL https://raw.githubusercontent.com/Vlancy/PullLens/main/bootstrap.sh | sh

It installs Git if it is missing, clones PullLens into a PullLens directory, and runs the installer. You will be asked two things: the address the instance will be reached at, and whether to fetch a free HTTPS certificate for it.

If you would rather read a script before piping it into a shell - a reasonable instinct - download it first. Nothing is lost:

curl -fsSL -o bootstrap.sh https://raw.githubusercontent.com/Vlancy/PullLens/main/bootstrap.sh
less bootstrap.sh
sh bootstrap.sh

Or skip the bootstrap entirely and do what it would have done:

git clone https://github.com/Vlancy/PullLens.git
cd PullLens
./install.sh

All three end in the same place. The installer will:

  • Check for Git and Docker, and install them if missing
  • Fetch the PullLens image and start the application, queue worker, scheduler, PostgreSQL, Valkey and websocket containers
  • Generate the application key and run all database migrations
  • Create the first administrator account
  • Print the URL and the login details
  • Offer to set up HTTPS with a free Let's Encrypt certificate - skippable, and skipped by default
Set an administrator password

In production, ADMIN_PASSWORD must be set in .env before the database is seeded - PullLens refuses to invent one for you. Outside production it generates a random password and prints it once. Copy it: it is not stored anywhere else.

Serve a production instance over HTTPS

A browser will not store a Secure cookie that arrived over plain http://. On an instance reached at http://your-host or at a bare IP address the session cookie and XSRF-TOKEN are dropped on every response, and the login form - along with every other form - comes back 419 Page Expired.

The installer keeps SESSION_SECURE_COOKIE in step with APP_URL: false when the URL is not HTTPS, so that logging in still works, and true once it is. In production PullLens forces the cookie back on by itself as soon as APP_URL is an https:// address, so the flag cannot be downgraded by accident. If you edit .env by hand, keep the two in agreement or rerun ./install.sh.

A plain-HTTP instance carries its sessions in cleartext, and anyone on the network path can read one and take over the account. Treat it as a state to pass through rather than settle in: put a reverse proxy or Cloudflare terminating TLS in front of the containers - X-Forwarded-Proto is already trusted - and set APP_URL to the https:// address.

Setting up the .env file

Everything PullLens needs to know about your instance lives in one file, .env, in the directory you cloned into. You do not create it by hand: ./install.sh copies .env.example to .env the first time it runs, generates the application key, and asks you for the address the instance will be reached at.

Re-running the installer never overwrites what is already there, so editing .env is safe and your secrets survive every update.

To change a setting afterwards:

nano .env          # or your editor of choice
./install.sh       # applies it and rebuilds the caches
Always rerun the installer after editing

PullLens caches its configuration for speed. A value changed in .env is not read until the caches are rebuilt, so an edit on its own appears to do nothing. ./install.sh does it for you; docker compose exec app php artisan optimize is the shorter way if the stack is already running.

The three you are most likely to touch first:

VariableWhat to set it to
APP_URLThe address visitors actually use. See below.
APP_PORTThe port on the server PullLens answers on. 80 by default.
ADMIN_EMAILThe first administrator account, created on the first run.

The full list worth reviewing is further down.

Pointing PullLens at your domain

APP_URL is the address PullLens believes it lives at. It is not cosmetic: it is used for the links inside every review it posts, the callback address GitHub sends webhooks to, the canonical URL search engines index, and the decision about whether the session cookie is marked Secure. If it is wrong, reviews link to the wrong place and webhooks never arrive.

Point your domain's DNS A record at the server's public IP address first, and wait for it to resolve. Then:

nano .env
APP_URL=https://pulllens.example.com
./install.sh

That is all that is needed when something else already terminates HTTPS for you. If you want PullLens to get its own certificate, skip straight to the next section - the script sets APP_URL for you as part of the job.

Changing the port

PullLens answers on port 80 by default. If something else on the server already owns it, change APP_PORT:

APP_PORT=8080

Then the address becomes http://your-server:8080, and APP_URL has to say so too - the port is part of the address:

APP_URL=http://your-server:8080
The two have to agree

APP_PORT is where the container listens; APP_URL is what PullLens tells the outside world. Change one without the other and the site loads while its links, webhooks and assets point somewhere that is not there.

HTTPS with a free certificate

A production instance should not be left on plain HTTP: sessions travel in the clear, and anyone on the network path can read one and take over the account. PullLens can get its own certificate, free, and keep it renewed.

./install.sh asks at the end of an install whether to set it up, and defaults to no. To add one later, to an instance that is already running:

./install.sh --https

Or without the questions:

./install.sh --https pulllens.example.com you@example.com

--https goes straight to the certificate step - it does not pull images, run migrations or reseed anything.

When not to use it

If anything already terminates HTTPS in front of PullLens - Cloudflare's proxy, a load balancer, a Kubernetes ingress, a company gateway, or another web server on this same host - do not run it. The request would fail: Let's Encrypt proves you own the domain by fetching a file from this server over port 80, and whatever sits in front answers instead.

There is nothing to install in that case. Set APP_URL to the https:// address your visitors use and rerun ./install.sh. PullLens already trusts X-Forwarded-Proto, so it will generate https:// links and keep the session cookie Secure.

What it does

Nginx inside the stack takes ports 80 and 443 itself, a certbot container requests a free Let's Encrypt certificate, and renewal runs twice a day for as long as the stack is up. Nothing is installed on your server - no system packages, no host web server, no root needed beyond what Docker already uses. It also moves APP_URL, ASSET_URL and SESSION_SECURE_COOKIE to the https:// address for you.

Before contacting Let's Encrypt it checks the things that usually go wrong, so a failed attempt costs you nothing:

  • the domain is a real hostname - Let's Encrypt will not issue for a bare IP address or localhost
  • the domain resolves, and resolves to this server; if it points somewhere else that usually means a proxy such as Cloudflare is in front, and the section above is the one you want
  • APP_PORT is still 80, because anything else means something on this host already owns the port PullLens needs

If issuance fails, nothing is changed and PullLens carries on over plain HTTP.

Leave port 80 open

It is not redundant once HTTPS works. It redirects visitors to HTTPS, and it carries the renewal challenge every 60 days. Close it and renewal fails silently on a site that looks perfectly healthy - until the certificate expires.

CommandWhat it tells you
docker compose logs certbotRenewal activity
docker compose exec certbot certbot certificatesWhich certificates exist and when they expire

Re-running is safe: a certificate that is still valid is kept.

Using your own proxy instead

Nothing stops you putting Nginx, Caddy or HAProxy on the host in front of the stack. Set APP_PORT to a free port so your proxy can have 80 and 443, point it at that port, forward X-Forwarded-Proto, set APP_URL to the https:// address, and rerun ./install.sh. PullLens does not manage that proxy or its certificate.

Settings worth reviewing

These live in .env. The defaults in .env.example are production-appropriate; these are the ones most worth a second look.

VariableWhat it does
APP_URLThe public URL of your instance. Used for webhook callbacks and links in reviews. Must be correct.
APP_DEBUGKeep false. Debug mode exposes stack traces and configuration to anyone who triggers an error.
SESSION_SECURE_COOKIESend the session cookie only over HTTPS. Set for you by the installer to match APP_URL, and forced on in production whenever APP_URL is HTTPS. Leave it true on a plain-HTTP instance and every login answers 419 Page Expired. See Install.
REGISTRATION_ENABLEDLeave false. Accounts are created by an administrator; there is no public sign-up.
HOMEPAGE_LOGINSet true on an internal instance: / serves the login screen instead of the landing page, and /docs stops responding, so nothing is readable before sign-in. Default false.
HIDE_LOGINTakes the Log in button off the landing page while leaving /login working for anyone who has the address. Ignored when HOMEPAGE_LOGIN is on. Default false.
MATOMO_URL, MATOMO_SITE_IDReport landing page visits to your own Matomo instance. Both are required; empty by default, and the script is never emitted on a signed-in page.
META_TITLE, META_DESCRIPTION, META_KEYWORDSThe title, description and keywords search engines and assistants index the landing page by. The defaults describe PullLens; override them on a branded instance.
META_IMAGE, META_IMAGE_ALT, META_LOCALE, META_THEME_COLORThe link-preview card WhatsApp, Slack and LinkedIn render, its alt text, the Open Graph locale and the browser theme colour.
WEBHOOK_REQUIRE_SIGNATUREReject webhooks without a valid signature. Always enforced in production.
REDIS_QUEUE_RETRY_AFTERMust stay above the longest job timeout (300). Lower it and a slow review can be executed twice.
LOG_LEVELwarning in production. debug is noisy and records request context.
TASK_TRACKER, TASK_TRACKER_BASE_URLTurns detected issue keys such as PROJ-451 into links to your tracker.

Updating

./update.sh

Pulls the latest code and the matching PullLens image, restarts the containers and runs any new migrations. The image is fetched before anything is stopped, so a failed download leaves the running instance alone. Run php artisan migrate after a manual upgrade if you are not using the script.

Trying it without connecting anything

To explore the interface with realistic data before wiring up GitHub, seed a demo dataset:

php artisan db:seed --class=DemoDataSeeder

This creates three fictional repositories, five fictional developers and a few dozen pull requests with reviews, findings and tasks. Every screenshot in this guide comes from that seeder. Do not run it on a real installation.
